Strong in-process

Problem.   • leverage: one interface, 8+ call sites
  • deletion test: removing it today distributes complexity — it wants to exist
  • tests: pure functions, no Dexie, no jsdom
  • kills the two disagreeing UI mappings

Strong ports & adapters

Problem. The factory is a pass-through so callers bypass it (new IndexedDBResultRepository() in two plugins); per-repo CRUD ceremony is duplicated 8×; and with no substitutable seam, the data layer has zero test coverage — the only available strategy is vi.mock-ing 25 factory names per test.

Solution. A parameterized Table module owning not-found and DBError wrapping, with two adapters — Dexie in production, in-memory in tests — behind one provider function replacing the 25 shallow factories.

  • typo debt (getCollectonLiveRepository) disappears with the factory
Not an IoC container. Doc 12's rejection of Awilix stands — this deepens the existing factory seam; it adds no injection framework.

4 · Extract the queue engine from the saga

Worth exploring local-substitutable

state/sagas/workers.ts:112–366 (startWorker loop) · 373–407 (initWorkersStatus) · hooks/useJobRealtime.tsx:48–176 · plugins/workers/layoutExtraction.ts · customWorker.ts

Before — the call graph of "run a task"

Problem. Answering "what happens between dispatch and persisted result" requires holding seven modules and ~900 lines in your head; the engine reads module-global registries and Date.now(), so nothing is testable — zero tests touch it, and the stop-listener race leaks a parked waiter per completed worker.

Solution. A headless queue engine module accepting ports (repository, clock, notifier); the saga, the realtime hook and startup recovery become thin adapters over run. Built on top of C1's status law.

  • one place to answer lifecycle questions
  • tests through one interface, no jsdom
  • saga shrinks to a takeEvery adapter
  • POSTING path gets one owner
Aligned with the project's own plan (docs 04/10: retire Redux-Saga). The engine makes that retirement a swap of one adapter, not a rewrite.

Top recommendation

1 · One home for the Worker status law

Workers are the codebase's hottest subsystem by commit volume, and its governing law — how task statuses move and how a Worker's status derives from its queue — already lives in four drifting copies, producing visibly contradictory behaviour (two disagreeing status→icon mappings, a canvas-scope gate that reads collection scope, an interface that promises ids and returns []). It is the smallest candidate on this page, pure and testable from day one, and it is the seam candidates 3 and 4 build on: deepening it first makes the queue-engine extraction a re-cabling job rather than a redesign.
